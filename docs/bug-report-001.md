## 二、bug 产生原因

测试脚本 `loginByMobileUI()` 点击"登录"后未等待登录完成（token 尚未写入 localStorage）即返回；调用方立即跳转受保护的详情页，路由守卫 `RequireAuth` 检查 localStorage 无 token，按设计重定向回登录页。

本质是**测试脚本与登录请求的时序竞态**：

```
测试:   点"登录" ──→ click返回 ──→ 立刻goto商品详情 ──→ 等"加入购物车"按钮
页面:        │            │              │ 检查token: 没有!  → 踢回登录页
后端:        └──收到登录请求──（处理中）──────┘ 登录响应这时才回来，token写好了
```

- 本地机器：登录响应先于跳转完成 → 详情页正常打开 → 侥幸通过
- CI 机器：时序相反 → 被重定向回登录页 → 稳定失败

## 三、bug 解决方法

1. 在 `loginByMobileUI()` 点击登录后增加显式同步点，等待登录成功的确定信号（URL 跳转商品列表）后再返回：

```ts
await page.getByRole('button', { name: '登录' }).click();
await expect(page).toHaveURL(/\/products$/); // 等待 token 写入 localStorage 后跳转
```

2. 同步排查并修复后台 UI 的 `loginByUI()` 同类隐患（等待 `/dashboard`）。
3. 回归验证：本地全量 20 passed（27.5s）；GitHub Actions CI 全量 20 passed。

## 五、经验沉淀

- 缺陷分类：产品 bug / 测试脚本 bug / 环境数据问题，先分诊再处理。
- "本地过、CI 挂"优先怀疑时序竞态（flaky），手工验证对竞态类问题基本无效（人无法用机器速度复现），应以失败快照、trace、日志为证据。
- 测试辅助函数应保证"动作完成"后再返回（契约：调用后登录态已建立），调用方不应依赖时机运气。
- 重试（retry）是止痛药不是治疗：修复根因前可临时设置上限，长期依赖重试会侵蚀测试结果可信度。
