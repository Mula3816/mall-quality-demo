| **测试步骤** | 1. admin 创建库存为 5 的测试商品；2. buyer 加购该商品 2 件并下单（下单扣减库存 5→3）；3. 查询库存断言为 3；4. 调用取消订单接口；5. 查询库存断言恢复为 5 |

| **实际结果** | 取消订单成功（状态变为 canceled），但库存仍为 3，扣减的 2 件库存未回补。测试断言失败：`Expected: 5, Received: 3` |

## 二、bug 产生原因

**库存扣减与回补不成对**：

- 下单时 [create_order](mall-backend/app/main.py) 会按购物车扣减商品库存（`product.stock -= item.quantity`）。
- 取消订单时 [cancel_order](mall-backend/app/main.py) 只调用 `apply_order_status(order, "canceled")` 修改订单状态，**没有任何库存回补逻辑**。
- 订单状态机允许 `created` 和 `paid` 两种状态取消，两条路径均存在该问题。

**影响**：用户取消订单后库存凭空蒸发，造成虚假缺货——商品实际有货但系统显示库存不足，后续用户无法购买；后台"低库存商品"统计被污染；商家可能误以为商品售罄而错误补货。

## 三、bug 解决方法

在 `cancel_order` 中按订单商品快照回补库存：

```python
apply_order_status(order, "canceled")
# 取消订单返还库存：下单时已扣减，取消必须回补，避免库存凭空蒸发。
# 商品可能已被后台删除（订单快照无外键），此时跳过即可。
for item in order.items:
    product = db.get(Product, item.product_id)
    if product:
        product.stock += item.quantity
db.commit()
```

要点：

1. **幂等性由状态机保证**：`canceled` 是终态，再次取消会被 400 拒绝，因此回补逻辑只会执行一次，不会重复返还。
2. **容错**：`order_items.product_id` 是裸外键（商品快照），商品可能已被后台删除，`db.get` 返回 `None` 时跳过，取消订单不因商品不存在而失败。

## 五、经验沉淀

- **测试先行的价值**：先写失败用例再修复，证明测试确实能抓住这个缺陷（如果先修复再写测试，测试可能是"永远通过"的摆设）。
- **数据一致性要成对思考**：凡是"扣减"型操作（库存、余额、库存占用），必须同步设计对应的"回补"路径——下单扣库存、取消回库存；支付扣款、退款回款。只设计一头必然出账实不符。
- **状态机即幂等保障**：终态不可再次流转，天然保证副作用（回补）只执行一次，修复时可放心按"每单回补一次"实现。
- **测试数据自清理**：用例自行创建商品并在结尾删除，保证可重复执行、不污染共享测试库。
